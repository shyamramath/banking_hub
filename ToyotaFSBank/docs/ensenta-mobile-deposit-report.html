01Executive summary

We should integrate natively with the Ensenta Mobile API (Multi-Check) through our own Deposit Gateway service. The mobile app captures check images with Mitek MiSnap, and the gateway runs the SOAP conversation with Ensenta using a Jack Henry–issued client certificate.

What it is

Ensenta Consumer Mobile and Business Mobile are Jack Henry's mobile remote deposit platforms. They process check images, score each check against more than 200 risk factors, and return items for review before posting.

How to onboard

Confirm we are contracted for Ensenta (not SmartPay). Then get a UAT PartnerId and client certificate from EPS Tech Integrations, build and test, and pass Jack Henry's integration certification before getting production credentials.

How to integrate

A SOAP/XML API split into two services, sign-on and deposit. A deposit is a short conversation: start a session, create a batch, add checks, poll, review risk flags, post, end the session.

What we own

User enrollment and eligibility, image capture quality, the review UX for flagged checks, session handling, and mapping Ensenta error codes to clear messages for the customer.

Note on the code and field values. This report follows Jack Henry's public developer guides. The WSDL and the API Reference sit behind the developer portal login, so the code samples are a starting point. Some field values (tender type, image category, account type codes) need confirming with Jack Henry.

04Reference architecture

The mobile app talks only to our Deposit Gateway. The gateway holds the Ensenta credentials, decides who may deposit, and makes every call to Jack Henry.

05Deposit workflow

Ensenta's API is a conversation, not one submit call. The gateway uploads all checks, waits for processing, shows the customer any risk flags, and only then posts the batch.

  1. Start session. The gateway calls StartSession with the depositor's identity, device, IP address and the list of accounts they may deposit into. Ensenta returns a SessionToken, a SessionStateId and an index for each account.
  2. Create the batch. CreateDepositBatch with the account index, the number of checks and a description. The Amount field is not used, so send 0.00. Ensenta returns a DepositBatchId.
  3. Add each check. AddDepositItem with the item number, amount, tender type, image category, preprocessing state, and front and back images as Base64.
  4. Wait for processing. Call GetDepositBatchSummary until ItemCount matches the number of checks sent. If it doesn't yet, wait about 2–5 seconds and try again.
  5. Review each check. GetDepositItem returns the MICR line, the amount read from the image, the amount the user entered, status, funds-availability text and the risk factors. Each risk factor says whether it can be fixed or confirmed.
  6. Fix or confirm. UpdateDepositItems lets the user delete a check, confirm a flagged item, or correct the amount, MICR or images.
  7. Post. PostDepositBatch with the item numbers to deposit. Ensenta returns the transaction ID, receipt number, totals and status.
  8. End or continue. Call EndSession, or start another batch in the same session if the user deposits again.

07Authentication and security

Ensenta authenticates our server, not the customer: it checks a client certificate tied to our PartnerId, then issues a short-lived session for each depositor.

Client certificate

The TLS request must carry a previously issued x509 certificate, which Ensenta validates for our PartnerId and environment. We create certificate requests with Jack Henry's kit, and EPS Tech Integrations issues the certificates. UAT and production certificates are separate and not interchangeable.

Session

StartSession returns a SessionToken and SessionStateId that go on every later call. A session expires after 15 minutes of inactivity, and each successful request refreshes it.

Controls we add

  • Store the certificate and its private key in a secrets manager or HSM, never in the app or source control.
  • The mobile app authenticates to our gateway with our existing OAuth2/OIDC tokens. It never sees the certificate, PartnerId or Ensenta session values.
  • Only enrolled users with eligible accounts reach StartSession.
  • Never log SOAP payloads in production: they contain check images, account numbers and personal data.
  • Pass the real device ID and client IP: Ensenta uses them for risk scoring.
  • Rotate certificates before expiry, with a reminder well ahead of the date.

09Gateway code

The starter project (ensenta-mrdc-sample.zip) is a Spring Boot service that generates SOAP classes from the WSDL and runs the full workflow. The extracts below show the two parts that matter most: mutual TLS and the deposit flow.

Mutual TLS for the SOAP clients (Spring WS)

@Bean
HttpsUrlConnectionMessageSender mutualTlsSender(EnsentaProperties props) throws Exception {
  KeyStore ks = KeyStore.getInstance("PKCS12");
  try (InputStream in = props.clientCert().keystore().getInputStream()) {
    ks.load(in, props.clientCert().keystorePassword().toCharArray());
  }
  KeyManagerFactory kmf = KeyManagerFactory.getInstance(KeyManagerFactory.getDefaultAlgorithm());
  kmf.init(ks, props.clientCert().keystorePassword().toCharArray());

  HttpsUrlConnectionMessageSender sender = new HttpsUrlConnectionMessageSender();
  sender.setKeyManagers(kmf.getKeyManagers());   // Ensenta validates this cert for our PartnerId
  return sender;
}

Deposit flow (MobileDepositService)

public ReviewResult submit(String userId, DepositorContext device,
                           String toAccount, String description, List<CheckImage> checks) {
  AccountHolder holder = eligibility.eligibleHolder(userId);        // we own enrollment
  DepositorContext ctx = sessionFor(userId, device, holder);        // StartSession or reuse
  int accountIndex = indexOf(userId, toAccount);

  long batchId = ensenta.createDepositBatch(ctx, accountIndex, checks.size(), description);
  for (int i = 0; i < checks.size(); i++) {
    CheckImage c = checks.get(i);
    ensenta.addDepositItem(ctx, batchId, i + 1, c.amount(), c.frontBase64(), c.backBase64());
  }

  BatchSummary summary = waitForItems(ctx, batchId, checks.size()); // poll 2-5 s with backoff
  List<DepositItem> items = summary.itemNumbers().stream()
      .map(n -> ensenta.getDepositItem(ctx, batchId, n))           // risk factors for review
      .toList();
  return new ReviewResult(batchId, summary, items);
}

Gateway API for the mobile app

POST /api/mobile-deposits                  -> upload checks, returns items + risk factors
POST /api/mobile-deposits/{batchId}/post   -> apply fixes/confirmations, post, returns receipt

10Onboarding to Jack Henry

Onboarding runs in four phases with three gates, and ends with Jack Henry's integration certification and a hand-off to their Implementations team for production credentials.

Step by step

  1. Confirm the contract. Check with our Jack Henry relationship manager that we are licensed for Ensenta Consumer Mobile (and Business Mobile if needed), not SmartPay RDA or mRDC. Jack Henry's own guidance tells developers to confirm which platform their company is contracted for.
  2. Get developer access. Register on the Jack Henry Payments developer portal (api.payments.jackhenry.com) to reach the guides, API Reference and Downloads page.
  3. Request a UAT PartnerId by emailing EPS.TechIntegrations@jackhenry.com.
  4. Get certificates. Download the Mobile Certificate Request kit, create UAT and production certificate requests, and send them to EPS Tech Integrations. Install each issued certificate on the machine that created its request, then export it to our secrets store.
  5. Download the WSDL for the sign-on and deposit services, and generate the client classes.
  6. Build the Deposit Gateway, MiSnap capture in the app, the eligibility service, the review screens and error handling.
  7. Test in UAT end to end: single and multi-check deposits, rejects, confirmable risk factors, session expiry, limits and duplicate checks.
  8. Certify. A Jack Henry engineer builds a test plan for our integration. Certification generally takes about a week, longer if fixes are needed.
  9. Go live. Jack Henry's Implementations team runs the implementation project and issues production credentials. Launch to a pilot group first, then all customers.

11Risks

The biggest early risk is building against the wrong Jack Henry platform. After that, image quality and the review experience decide whether customers succeed.

RiskSeverityDetailMitigation
Wrong platformHighEnsenta and SmartPay have different APIs; "mRDC" is a SmartPay product name.Confirm the contract before any build work.
Image qualityHighBlurry or cropped images cause rejects and repeat attempts.Use MiSnap auto-capture; test on low-end devices.
Unknown posting pathMediumThe public guides do not describe how deposits reach our core.Get the posting design from Jack Henry in phase 1.
Session expiry mid-depositMediumSessions end after 15 minutes idle, for example while a user hunts for a second check.Restart the session once automatically; keep the batch state in the gateway.
Slow processingMediumItems are processed asynchronously, so the app can wait several seconds.Poll with backoff; show progress; time out with a clear message.
Review workloadMediumFlagged items need bank staff to review them.Staff the queue before launch; tune risk settings during the pilot.
Legacy SOAP stackMediumSOAP/XML with large Base64 images is heavier than REST and harder to debug.Keep it inside the gateway; give the app a simple JSON API.

Severity ratings are our own assessment for discussion.
