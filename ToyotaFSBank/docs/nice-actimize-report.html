01Executive summary

We should buy NICE Actimize's fraud (IFM-X), KYC (CDD-X or X-Sight Onboard) and screening (WL-X) modules on the X-Sight cloud platform. We would integrate them through one internal Risk Gateway service, so that our channel apps never call NICE directly.

What to buy

IFM-X for login, session, payment and new-account fraud. CDD-X or X-Sight Onboard for KYC risk rating. WL-X for sanctions and PEP screening. ActOne as the single case manager. If we are a community or mid-size bank, ask for a quote on Xceed AI FRAML too.

How to onboard

There is no self-serve sign-up. The path is sales contact, then NDA and discovery, vendor due diligence and a contract. After that, NICE or a certified partner runs an implementation that takes several months.

How to integrate

Synchronous risk calls at four points: account opening, login, high-risk session events and payment release. Everything else (customer data, transactions, case outcomes) moves asynchronously over Kafka or batch.

What to watch

NICE is selling the Actimize business. Write support, roadmap and change-of-control protections into the contract. Also design latency budgets and fallbacks before go-live.

Note on API details. NICE shares its API specifications, data dictionaries and deployment guides only under NDA. The message shapes, timeouts and code in this report are our proposed design. We should replace them with NICE's contract once we have it.

04Reference architecture

Our channel apps call only our own Risk Gateway. The gateway makes the real-time decision calls to NICE, and all other data reaches Actimize asynchronously over the event stream.

Responsibilities by layer

05Integration flows

Five flows cover the whole integration. The first three are in the customer's path and need a latency budget. The other two run in the background.

Flow 1: Digital account opening (fraud and KYC)

  1. The onboarding service collects the application with device and session data, and calls assessApplication on the Risk Gateway.
  2. The gateway calls our identity-proofing vendors (document and selfie, phone, email, device), or lets IFM-X New Account Fraud orchestrate them, and gets one identity risk score back.
  3. At the same time it sends name, date of birth, address and nationality to WL-X for sanctions and PEP screening.
  4. CDD-X or X-Sight Onboard computes the first KYC risk rating from the questionnaire, product, geography and screening result.
  5. The result is approve, approve with limits, refer to EDD, or decline. A referral opens an ActOne case.
  6. On approval, the core banking customer and account IDs go back to Actimize, so new-account monitoring starts from day one.

Flow 2: Login and in-session events

  1. The auth service calls assessLogin with customer ID, device fingerprint, IP and location, channel, and a behavioural biometrics score if we have one.
  2. IFM-X returns a score and an action: allow, step-up, or deny.
  3. The auth service enforces the action (OTP, push or passkey). It then sends the step-up result back as an event, so the customer profile keeps learning.
  4. High-risk in-session events (new payee, phone or email change, limit increase) use the same synchronous pattern. Low-risk events go over the stream asynchronously.

Flow 3: Payment release

Flow 4: Alerts and case management

Alerts from IFM-X, WL-X, CDD-X and SAM all land in ActOne. Analyst decisions (confirmed fraud, false positive, confirmed sanctions hit) must come back to our systems through a webhook or queue. We use them to release or return payments, restrict or close accounts, and file SARs. The same decisions become training labels for model tuning.

Flow 5: Data feeds

Customer, account and transaction data reaches Actimize in the background. See Data feeds for the full list.

06Risk Gateway design

The Risk Gateway is a Spring Boot service that is the only client of NICE. It keeps NICE's latency, outages and schema out of our channel code.

Design rules

  • Channel apps never call NICE directly. Every decision point goes through the gateway.
  • Each flow has a hard timeout set below NICE's contracted SLA, and a circuit breaker.
  • Each flow has a written fallback for when NICE is slow or down (table below).
  • Every request carries an idempotent eventId, so retries never score a payment twice.
  • Connection to NICE uses mTLS or OAuth2 client credentials. We send only the PII each module needs, and tokenise where the module allows.
  • Every request, response, fallback and final action is logged with a correlation ID, for audit and model governance.
  • We keep our own event schema and map it to NICE's inside the gateway. That limits lock-in if we ever change vendors.

Timeouts and fallbacks (proposed starting values)

These numbers are our proposal for discussion. We tune them once NICE commits to a response-time SLA and we have run performance tests.

FlowTimeout budgetFallback if NICE is slow or down

Illustrative Spring Boot gateway with Resilience4j

@Service
public class PaymentRiskService {

  private final ActimizeClient actimize;     // generated from NICE's NDA API spec
  private final FallbackPolicy fallback;
  private final DecisionAuditLog audit;

  @CircuitBreaker(name = "actimize-payment", fallbackMethod = "onFailure")
  @TimeLimiter(name = "actimize-payment")
  public CompletableFuture<RiskDecision> assess(PaymentRiskEvent event) {
    return actimize.scorePayment(ActimizeMapper.toVendor(event))
        .thenApply(RiskDecision::from)
        .whenComplete((d, ex) -> audit.record(event, d, ex));
  }

  private CompletableFuture<RiskDecision> onFailure(PaymentRiskEvent event, Throwable t) {
    RiskDecision d = fallback.forPayment(event);   // e.g. HOLD at or above the threshold
    audit.recordFallback(event, d, t);
    return CompletableFuture.completedFuture(d);
  }
}
# application.yml
resilience4j:
  timelimiter:
    instances:
      actimize-payment: { timeoutDuration: 500ms }
      actimize-login:   { timeoutDuration: 300ms }
  circuitbreaker:
    instances:
      actimize-payment:
        slidingWindowSize: 100
        failureRateThreshold: 20
        slowCallDurationThreshold: 400ms
        slowCallRateThreshold: 30
        waitDurationInOpenState: 30s

08Onboarding to NICE

Onboarding to NICE is an enterprise sales and implementation process in four phases, each closed by a gate. One independent review describes the implementation as taking months, with services typically costing EUR 200k–600k on top of a yearly licence priced by volume and modules (KI-Syndikat). Treat those cost figures as a rough guide only.

Step by step

  1. Contact sales. Use the contact or demo form on niceactimize.com, or email info@niceactimize.com. Say we are an online bank looking for digital fraud (IFM-X), KYC/CDD and sanctions screening, and ask whether Xceed fits our size.
  2. Sign an NDA and run discovery. The mutual NDA unlocks API specs, data dictionaries, deployment guides and security documents. In the scoping workshop, share channels, payment rails, volumes (logins and payments per day, peak TPS), customer count, regulators and existing vendors.
  3. Vendor due diligence. Run our third-party risk review: SOC 2 and ISO 27001 reports, data residency, encryption, pen-test results, business continuity and DR, sub-processors, and model documentation for our model-risk validation.
  4. Sign the contract. Fix the modules, deployment model, environments (dev, UAT, prod), response-time and availability SLAs, and who implements (NICE Professional Services or a partner). Include change-of-control protections (see Risks).
  5. Solution design. Map our data to NICE's model, design the Risk Gateway contracts and fallbacks, pick identity vendors from X-Sight Marketplace, and agree the first rules, models and ActOne workflows.
  6. Build and load data. Build connectors and streams, backfill history for profiling, configure policies and case queues, and connect case outcomes back to our systems.
  7. Test and tune. Run functional, peak-load, failover and fallback tests. Then run in shadow mode on live traffic, scoring without acting, to tune thresholds before any customer is blocked.
  8. Go live in stages. Turn on one flow at a time, for example login, then payments, then account opening. Track false positives, review volumes and latency at each stage.
  9. Operate. Tune models and thresholds regularly, monitor list updates, train analysts in ActOne, and keep documentation ready for examiners.

09Deployment options

Choose X-Sight SaaS unless a regulator or data-residency rule forces on-premise. It is faster to build, and NICE handles upgrades.

OptionSuitsWhat it means for usTrade-offs
X-Sight SaaS (on AWS)Most banks that are modernising. KeyBank runs its fraud and AML on it.Private network connection from our cloud or data centre. NICE runs the platform.Less control over when upgrades happen. Data leaves our network.
On-premise or private cloudStrict data residency, or a large on-premise estateWe host and run the Actimize servers, databases and upgrades.Highest effort and cost. New analytics arrive later.
Xceed AI FRAML (SaaS)Credit unions, community and mid-size banksPrebuilt data connectors and ready-made modelsLess room to customise than the enterprise modules

For a Spring Boot and Kafka team on AWS, SaaS fits naturally: the Risk Gateway as a Spring Boot service with Resilience4j, Kafka topics for transaction and outcome streams, and a private connection to X-Sight. We need to confirm the supported connection options with NICE.

11Open questions for the team

These eight questions need answers before the first NICE scoping call.

  • Are we an enterprise X-Sight customer or a Xceed-size institution? This decides which product line NICE quotes.
  • SaaS or on-premise, given our data-residency and regulator position?
  • Peak volumes: logins per day, payments per day, peak TPS, customer count.
  • Which payment rails are in scope: ACH, wire, RTP, FedNow, Zelle, cards?
  • Which identity-proofing and device vendors do we already use, and are they on X-Sight Marketplace?
  • What response-time SLA will NICE commit to for each flow, and do we accept the fallbacks proposed here?
  • NICE Professional Services or a partner to implement?
  • Which contract protections do we need for the Actimize ownership change?
